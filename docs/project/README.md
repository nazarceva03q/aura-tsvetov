# Устройство и состояние Ауры

Срез на 09.11.2026. Источники: корневой код Ауры и результаты настройки, присланные заказчиком. Это не независимый аудит личных кабинетов провайдеров.

## Что находится где

| Часть | Назначение |
|---|---|
| `index.html`, `business.js`, CSS, `products/`, `catalog/` | Статический сайт, карточки и форма. По сообщению заказчика размещены на REG.RU |
| `business.js` | Публичные контакты, адрес функции приёма и адрес публичного каталога; секретов здесь быть не должно |
| `bot/index.js` → `index.handler` | Общая функция: принимает вебхуки MAX и обращения сайта |
| `bot/src/bot.js`, `admin.js` | Общение с клиентами и управление каталогом; новый отдельный MAX-бот не создавался |
| `bot/src/notify.js` | Передаёт заявку в личный диалог владелицы с ботом; это не закрытая беседа VK «Бирюзы» |
| `bot/src/store.js`, `privateDb.js`, `objectStorage.js` | Частные JSON-данные, условные записи по ETag для защиты от гонок |
| `bot/src/retention.js`, `operation.js` | Сроки, квитанции исходящих сообщений, защита повторной отправки |
| `bot/cleanup.js` → `cleanup.handler` | Закрытая отдельная функция очистки того же MAX-бота |
| Частный бакет `aura-max-bot-data` | Заявки, вопросы, клиенты, сессии и технические квитанции |
| Публичный бакет `aura-catalog` | Каталог и фото товаров; клиентских заявок в нём быть не должно |

Путь данных: **браузер → общая Cloud Function → частное облачное хранилище / MAX**. REG.RU отдаёт страницы и может вести технические журналы. Российский хостинг страниц не заменяет выяснение расположения остальных хранилищ и условий провайдеров.

## Подтверждено в ходе настройки

- Основной бот снова отвечает после восстановления действующего MAX-токена.
- Доступ к Object Storage восстановлен после замены пары статических ключей; старый ключ удалён пользователем. Новая пара должна оставаться в обеих функциях.
- Проверка `SMOKE` вернула `maxDeleted: true`: отправка и удаление свежего сообщения работают.
- Реальный запуск APPLY удалил 12 просроченных записей, `errors: 0`.
- Следующий результат APPLY после настройки таймера: `scanComplete: true`, `cloudRemoved: 0`, `legacyUndated: 1`, `errors: 0`. Пользователь сообщил о возврате расписания на каждый час.
- Значения токенов, ключей, ID личных диалогов и содержимое клиентских обращений в документацию не записываются.

## Чего эти результаты не подтверждают

- Фактическое удаление сообщения MAX возраста 30 суток: проверялось свежее сообщение.
- Удаление входящих сообщений пользователя в личном диалоге, старых исходящих без квитанций, снимков экрана, экспортов, версий объектов и копий у людей/провайдеров.
- Готовность полного юридического комплекта, подачу в РКН, наличие оформленных полномочий доступа или актов уничтожения.
- Точную локацию и договорные сведения конкретной услуги REG.RU, Yandex Cloud и MAX. Их следует получить у поставщиков, не выводить из IP или названия бренда.

## Сроки в коде

Рабочие обращения, вопросы, сведения о клиентах и сессии — 30 суток от первого создания соответствующей записи. Повтор/просмотр срок не продлевает. Технические квитанции с идентификаторами без текста и контактов — до 37 суток от начала исходного срока. Это всё ещё технические идентификаторы, а не гарантированно обезличенные сведения.

У старых записей без дат — один миграционный срок от первого запуска новой версии; они видны в `legacyUndated`. Такой счётчик не означает ошибку. После истечения срока запись скрывается из рабочих меню, очистка выполняется ближайшим успешным проходом. При сбоях или большой очереди задержка может быть больше часа.

Постоянные старые хеш-метки в `processed_updates/` не затрагиваются. Они нужны для защиты повторов и не содержат текста заявок; их статус, необходимость и срок следует включить в техническую оценку, а не объявлять автоматически анонимными.
