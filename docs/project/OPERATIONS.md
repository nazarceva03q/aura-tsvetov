# Эксплуатация Ауры

## Публикация

Сайт находится на REG.RU по сообщению заказчика. Для обновления заменить только необходимые публичные файлы в корне сайта через защищённый доступ хостинга. Не загружать `.env`, `bot/`, `tests/`, документы разработки, частные данные и вложенный чужой проект. Не размещать архивы функций в общедоступном каталоге сайта. Коммит/push и выкладка на REG.RU — разные действия; автоматическая синхронизация этим изменением не настраивалась.

ZIP-функции загружаются **в Cloud Functions**, не в файловый менеджер REG.RU:

| Функция | Архив | Точка входа |
|---|---|---|
| Основной бот | `bot/aura-max-bot.zip` | `index.handler` |
| Очистка | `bot/aura-max-cleanup.zip` | `cleanup.handler` |

Сохранять текущие URL и секрет вебхука. Архивы не содержат рабочих ключей. Среда настройки: Node.js 22, 256 МБ, таймаут 120 секунд; не менять произвольно при загрузке.

## Рабочие настройки очистки

- `CLEANUP_APPLY=true`, `CLEANUP_SMOKE=false`.
- Частная функция `aura-max-cleanup`; публичный доступ не включать.
- Таймер вызывает `$latest` с расписанием `0 * * * ? *`: каждый час в :00, в том числе по Москве.
- Сервисному аккаунту таймера нужна роль `functions.functionInvoker`; статический ключ ему не требуется. Это отдельная роль от доступа функций к Object Storage.
- В обеих функциях действуют соответствующие друг другу `YC_S3_ACCESS_KEY` и `YC_S3_SECRET_KEY`, частный `YC_S3_BUCKET` и токен **одного и того же** MAX-бота. `MAX_OWNER_CHAT_ID` — один ID; `MAX_ADMIN_CHAT_IDS` — дополнительные администраторы через запятую, буква S верна.

## Наблюдение

В частном бакете смотреть `retention/last-result.json`: свежий `at` (UTC-миллисекунды), `mode: APPLY`, `errors: 0`. Счётчики относятся к одному проходу. `scanComplete:false` требует проверить последующее продолжение; `maxPending` и `unknownDelivery` требуют разбора, а не заявления «всё удалено». Во время эксплуатации проверять отчёт регулярно и после изменений функции/ключей; один успешный запуск не гарантирует будущую работу.

При отсутствии нового отчёта проверить состояние триггера, его аккаунт, функцию и тег версии. Проверка через «Тестирование» `{}` допустима; при APPLY она действительно удаляет просроченные записи.

## Ошибки и восстановление

| Ошибка | Действие |
|---|---|
| `STORAGE_READ_403_SignatureDoesNotMatch` | Проверить соответствие ID и секрета одной статической пары, отсутствие лишних символов. Сначала заменить во всех использующих функциях, затем отзывать старую пару |
| `DELIVERY_OUTCOME_UNKNOWN_ERR_INVALID_CHAR` | Проверить переменные заголовков, прежде всего MAX-токен: без переносов и посторонних символов |
| `SMOKE_SEND_FAILED_HTTP_401_verify.token` | Взять действующий токен существующего бота у владельца в MAX для бизнеса, заменить в обеих функциях, сохранить и выбрать новую версию |
| `DELIVERY_OUTCOME_UNKNOWN…` | Отправка могла состояться. Не повторять реальные заявки вслепую; проверить чат и техническую квитанцию |

Токены не отправлять в чат и не коммитить. Не отключать проверку TLS ради обхода ошибки. Успешный SMOKE проверяет только свежее сообщение; после него вернуть SMOKE=false.

При необходимости приостановки отключить триггер или APPLY, не удалять бакеты/бота. Срок хранения при остановке не отменяется: просроченные сведения нужно обработать другим способом. Не откатывать основной бот к версии без условных записей, пока очистка меняет те же JSON-файлы.

## Граница ответственности

Обязательные бухгалтерские документы, претензии и согласованные долгие заказы организуются отдельно от 30-дневного рабочего журнала. Технический `last-result.json` не является актом уничтожения и не содержит достаточного журнала по приказу РКН № 179. Точный порядок подтверждения уничтожения ещё предстоит реализовать и утвердить; не пытаться заменить его сохранением всех контактов бессрочно.
