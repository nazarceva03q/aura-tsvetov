# Аура: включение очистки через 30 суток

Код подготовлен 09.11.2026 для проекта `aura-tsvetov/bot`. Папка `za tsvetkom` и ресурсы «Бирюзы» не используются. Существующий MAX-бот остаётся общим для управления и заявок. В облаке нужна ещё одна **закрытая функция**, а не второй бот. Обновление статуса 09.11.2026: по результатам, присланным пользователем, основная функция работает, SMOKE подтвердил удаление свежего сообщения, APPLY удалил 12 записей без ошибок, таймер проверен и возвращён на каждый час. Удаление сообщения возраста 30 суток этим не подтверждено. Сайт перенесён на REG.RU по сообщению заказчика. Актуальное состояние: [документация проекта](../docs/project/README.md).

## Что изменилось

- Заявки, вопросы, клиентские телефоны и сессии имеют предел хранения 30 суток от первого создания соответствующей записи. Повтор события, просмотр и ответ не продлевают срок. После истечения данные не показываются меню и очищаются по расписанию.
- Телефон для признака «Повторный заказ» помнится только в этом окне, а не бессрочно. Новое обращение после окончания окна создаёт новую запись. У старых записей с датой используется эта дата. Для старых записей **без даты** действует один фиксированный миграционный срок: 30 суток от первого запуска новой версии; они отдельно считаются в `legacyUndated`. Это не подмена даты поступления заявки.
- Все **новые исходящие сообщения** через MAX API, включая пересланные заявки, контакты, ответы и меню, получают минимальную квитанцию с ID и сроком. Для просмотра существующей заявки квитанция ограничивается её сроком; сам текст в квитанции не хранится. Через 30 суток выполняется запрос удаления. Управление товарами и файлы каталога не удаляются.
- Минимальные технические квитанции, содержащие ID сообщений и хеши, но не текст и контакты, удаляются не позднее 37 суток от исходного начала срока. Это технические идентификаторы, их нельзя называть гарантированно анонимными данными.
- Одновременная запись и очистка общих JSON-файлов защищены ETag/условной записью. Сбой чтения не превращается в пустую базу. Нельзя откатывать только код бота к старой версии, оставляя очистку активной: старые записи не защищены CAS.
- Новый сайт передаёт стабильный ID повторной отправки в рамках открытой страницы. Повтор с тем же ID и другим содержанием отклоняется. При неопределённом ответе MAX повторная отправка сообщения не выполняется бесконечно. Для старых уже открытых форм без ID полная идемпотентность не обещается; после обновления обновить страницу.

## Ограничения, которые важно знать заранее

1. Это **30 суток от создания**, даже если покупатель заказал на далёкую дату. После срока ответ по старой кнопке невозможен. Подтверждённые договоры, кассовые и иные обязательные документы имеют отдельные сроки и должны храниться по самостоятельным основаниям, а не в этом журнале обращений.
2. Входящее сообщение клиента в его личном диалоге с ботом MAX API удалять не позволяет. Клиент удаляет его средствами MAX; не обещать уничтожение всех копий переписки одной кнопкой.
3. Старые сообщения, отправленные до обновления без сохранённых ID, новая функция автоматически не находит и не удаляет. Их нужно разобрать и удалить вручную, где это доступно. Облачные старые записи с датами при APPLY могут удалиться уже при первом запуске.
4. Неопределённый ответ отправки может оставить сообщение без известного ID. Такие случаи учитываются в `unknownDelivery`, требуют разбора. Истечение срока облака от удаления MAX не зависит.
5. Успешный `SMOKE` подтверждает удаление **свежего** служебного сообщения. Фактическое удаление сообщения возраста 30 суток им не проверяется. Не выдавать локальные тесты с подменой часов за проверку возраста сообщения MAX.
6. Частные бакеты должны быть закрыты. При включённом версионировании перезапись JSON не уничтожает старые версии. Перед APPLY проверить старые версии, Object Lock и резервные копии. Не удалять версии каталога/публичных фото вместе с клиентскими записями. Не добавлять общий lifecycle на весь бакет.
7. `last-result.json` — технический отчёт, не подписанный юридический акт уничтожения по приказу РКН № 179. Порядок актов и выгрузок событий нужно оформить отдельно; не обещать, что весь юридический комплект сформирован кодом. Постоянные прежние хеш-метки `processed_updates/` не затрагиваются, содержимого заявок в них нет.

## Шаг 1. Проверить существующее хранилище

В **Yandex Cloud → Cloud Functions → существующая функция `aura-max-bot` → Редактор** посмотрите, какой `YC_S3_BUCKET` уже указан. Значения секретов никому не отправлять.

В **Object Storage → этот бакет → Настройки** убедитесь:

- чтение объектов, список и настройки — **с авторизацией**;
- нет версионирования, сохраняющего удаляемые личные сведения, Object Lock или неучтённых резервных копий. Если они есть — сначала разобрать их сроки и старые версии, не включать APPLY вслепую.

Публичный бакет из `YC_PUBLIC_S3_BUCKET` относится к каталогу, его не менять. Если клиентское хранилище и публичный каталог оказались в одном открытом бакете — остановиться и сначала разделить доступы.

## Шаг 2. Обновить общий бот

**Cloud Functions → `aura-max-bot` → Редактор → ZIP-архив**:

- архив: `bot/aura-max-bot.zip`;
- среда: **Node.js 22**;
- точка входа: **`index.handler`**;
- память: **256 МБ**, таймаут: **120 секунд**;
- текущие переменные MAX, Object Storage, публичного каталога и секрет вебхука оставить;
- сохранить новую версию. URL функции и подписку MAX не менять.

Новая версия начинает учитывать сообщения и сроки сразу. Очистку включает только отдельная функция ниже. Дождаться завершения возможных вызовов старой версии в пределах её прежнего таймаута, прежде чем включать APPLY.

## Шаг 3. Создать функцию очистки

**Cloud Functions → Создать функцию → имя `aura-max-cleanup` → Редактор**:

- архив: `bot/aura-max-cleanup.zip`;
- **Node.js 22**, точка входа **`cleanup.handler`**;
- **256 МБ**, таймаут **120 секунд**;
- **публичный доступ выключен**;
- подходящий существующий сервисный аккаунт «Ауры» с доступом к её частному бакету. Не использовать аккаунты/ключи «Бирюзы» и «За цветком».

Переменные скопировать **внутри консоли**, не в переписку:

| Переменная | Значение |
|---|---|
| `YC_S3_BUCKET` | То же имя частного бакета, что у основного бота |
| `YC_S3_ACCESS_KEY` | Действующий ключ с нужными правами к этому бакету |
| `YC_S3_SECRET_KEY` | Соответствующий секрет |
| `MAX_BOT_TOKEN` | Токен того же MAX-бота |
| `MAX_OWNER_CHAT_ID` | Тот же ID владелицы |
| `CLEANUP_APPLY` | **`false`** |
| `CLEANUP_SMOKE` | **`false`** |

`YC_PUBLIC_S3_BUCKET` очистке не нужен. Ключи не создавать заново без необходимости. Боту и очистке требуются Get/Put для `customers.json`, `questions.json`, `leads.json`, `sessions.json`, `recent_updates.json`, Get/Put для `retention/*`; очистке дополнительно ListBucket и DeleteObject только для `retention/messages/*`. Прежние права бота на каталог и `processed_updates/*` сохранить. В подходящем существующем аккаунте роль `storage.editor` на частном бакете покрывает нужные операции; не выдавать editor/admin на всё облако ради таймера.

## Шаг 4. Один проверочный запуск

1. В новой функции открыть **Тестирование**, тело **`{}`**, запустить. Ожидается `mode: PREVIEW`, `errors: 0`. `cloudRemoved` в PREVIEW — количество записей, которые **будут** удалены, а не уже удалённых. Посмотреть `legacyUndated` и старые заявки до включения.
2. В Редакторе временно поставить **`CLEANUP_SMOKE=true`**, сохранить. Ещё раз Тестирование `{}`. В чат владелицы отправится одно сообщение **«Служебная проверка очистки…»**, затем бот попробует удалить именно его. Ожидается **`mode: SMOKE`, `maxDeleted: true`**. Владелица подтверждает, что сообщение исчезло. При false сначала разобраться с правами/ответом MAX; не обещать удаление сообщений.
3. Вернуть **`CLEANUP_SMOKE=false`** и сохранить. Не оставлять его включённым у таймера.
4. Через бота или обновлённую форму отправить одну вымышленную заявку без реальных контактов; проверить обычное получение и работу меню. Ранее существующие тесты локально повторять вручную не нужно.

## Шаг 5. Включить очистку

В `aura-max-cleanup` установить **`CLEANUP_APPLY=true`**, **`CLEANUP_SMOKE=false`**, сохранить. Тестирование `{}` — теперь ответ `mode: APPLY`, `errors: 0`. При наличии просроченных данных они удаляются. Если входящих заявок нет — нули нормальны, но это не подтверждение удаления старых сообщений.

MAX проверяется по `success === true`, одного HTTP 200 недостаточно. Повторы удаления — до 5 попыток с интервалом не менее суток, с ограничением скорости. Квитанция окончательно удаляется по техническому сроку. Ошибки MAX не продлевают хранение облачного содержимого.

## Шаг 6. Настроить таймер

1. **IAM → Сервисные аккаунты**: выбрать подходящий существующий аккаунт таймера «Ауры» или создать **`aura-cleanup-timer`**. Статический ключ ему не нужен.
2. На функции **`aura-max-cleanup` → Права доступа** выдать этому аккаунту **`functions.functionInvoker`**. Публичный доступ остаётся выключенным. Если интерфейс не позволяет, в Cloud Shell своего каталога выполнить, подставив ID аккаунта: `yc serverless function add-access-binding --name aura-max-cleanup --role functions.functionInvoker --service-account-id ID_АККАУНТА`.
3. **Cloud Functions → Триггеры → Создать → Таймер**. Имя **`aura-cleanup-hourly`**. Расписание — **«Каждый час»**, либо cron **`0 * * * ? *`** (UTC).
4. Вызываемая функция **`aura-max-cleanup`**, тег **`$latest`**, сервисный аккаунт **`aura-cleanup-timer`** (или выбранный действующий). Тело не требуется; оставить пустым. Сохранить.

## Шаг 7. Проверить и обновить сайт

- После срабатывания таймера: в частном бакете должен обновиться **`retention/last-result.json`**. Смотреть время `at`, `mode: APPLY`, `errors`, `scanComplete`, `unknownDelivery`, `maxPending`. Это данные одного прохода/порции, не число всех заявок навсегда. `scanComplete:false` означает продолжение на следующем запуске с сохранённого курсора. Файл не делать публичным; при проблемах просмотра использовать Тестирование функции и приватные логи вызова.
- Обновлённый корневой **`index.html`** публикуется на **REG.RU**, где размещён сайт. Заменять только нужный публичный файл в корне сайта; архив функции, `.env`, `bot/` и частные данные туда не загружать. Коммит/push в GitHub сам по себе не подтверждает публикацию REG.RU. Каталог, домен, CSS и фото ради юридического текста заменять не нужно.
- Политика описывает 30 суток, технические квитанции и ограничения MAX. Оставшиеся юридические задачи перечислены в [плане](../docs/legal/PLAN.md). Настройка таймера не заменяет документы, уведомление РКН и подтверждение уничтожения.

## Как остановить

Отключить триггер `aura-cleanup-hourly` или поставить `CLEANUP_APPLY=false` в функции и сохранить. Не удалять бакеты, каталог или основного бота. Остановка удаления не отменяет срок хранения: при длительной остановке нужен другой способ исполнения срока. Возобновление APPLY удалит накопившиеся просроченные записи.
